# 4265 Auto Replay

Replays every PathPlanner auto in [`secret-city-wildbots/2026-Robot`](https://github.com/secret-city-wildbots/2026-Robot)
in the browser, using trajectories generated by the **same PathPlannerLib the robot runs**.

There are no PathPlanner videos to replay — PathPlanner has no video export, and its GUI
animation is rendered live from path data and never captured. This rebuilds that preview from
the `.path`/`.auto` files directly, which scrubs, stays in sync when a path is re-tuned, and
needs no recording step.

## Run it

```bash
./regen.sh                       # generate viewer/autos.json from 2026-Robot@dev
java Serve.java 8265 viewer      # -> http://localhost:8265
```

`regen.sh` needs the WPILib JDK (defaults to `/c/Users/Public/wpilib/2026/jdk`). `viewer/` is
static — any file server works, and `autos.json` is committed so the site runs without Java.

## Pages

- **`index.html`** — menu. Pick which teams to replay together, then "Replay together". Each
  card links to that team's own view. Unavailable teams (no usable autos) are shown greyed with
  the reason.
- **`single.html?team=<n>`** — one team's autos, velocity-coloured, scrub/play (defaults to 4265).
- **`alliance.html?teams=<csv>`** — the chosen teams' autos at once on one field.

## Alliance view (multi-team)

`alliance.html` plays **several teams' autos at once on one field** to check for collisions and
coordination — the thing PathPlanner itself can't do. Pick one auto per team; each robot drives
in its team colour with its own dimensions and features, on a shared clock. A **closest-approach**
readout reports the minimum centre-to-centre distance per pair over the whole run (bounding-circle
based — a flag means "look closer", not a guaranteed hit), and overlapping robots get a red link.
The team subset comes from the menu via `?teams=4265,117,2539`.

Other teams' data comes from their own repos:

```bash
./generate-team.sh FRC2539/2026-rebuilt 2539     # -> viewer/autos-2539.json
```

It swaps their `pathplanner` folder through 4265's build, so trajectories use **their** robot
config but the identical PathPlannerLib. **2026 autos only** — a 2025 auto is on a different
field and lands in the wrong place. Then add the file to `viewer/teams.json` with a colour
(or a `"unavailable"` reason and no `file` to show it greyed in the menu).

Ships with the WVROX teams that have usable 2026 autos: 4265, 117 (Steel Dragons), 1466 (Webb
Robotics), 2539 (Krypton Cougars). 620 (Warbots) is listed but unavailable — its repo has only
PathPlanner's placeholder "Example Auto" and an incomplete config (no swerve module positions,
which makes `RobotConfig.fromGUISettings()` throw).

### Which WVROX teams have public autos

Of the 30 teams at WVROX, a GitHub sweep (verified against each project's `.wpilib` team number,
so wrong-team repos are rejected) found **9 with public PathPlanner autos**: 117, 620, 1086,
1466, 1533, 2539, 6239, 8728, and 4265. Only some are current-season 2026 (117, 620, 1466, 2539,
4265); the rest are 2025 and can't share the 2026 field. This confirms the earlier call: a
"browse any opponent's autos" tool isn't viable — most teams post nothing, and the reliable path
is alliance partners sharing files at the event.

## How it works

```
2026-Robot@dev ──> AutoDumper (real PathPlannerLib) ──> autos.json ──> viewer (canvas)
```

The **viewer does no physics.** It plays back precomputed samples, so it cannot disagree with
the robot. All fidelity lives in the generator, which delegates to `PathPlannerLib-2026.1.2`
with the robot's own `settings.json` (mass 45.36 kg, Kraken X60, 35 A limit, COF 1.2).

`AutoDumper` walks each auto's command tree, resolves `path` nodes to `.path` files, chains the
segments (carrying end velocity between them), and samples pose/heading/velocity at 50 Hz.
`regen.sh` injects it into a throwaway clone of the robot repo, because that's where GradleRIO
already resolves PathPlannerLib and the WPILib natives.

## Read this before trusting a number

**Times are driving time only.** Named commands (`Shoot`, `Intake`, …) carry no duration in
PathPlanner data, so an auto's real runtime is longer than what's shown. **This tool cannot tell
you whether an auto fits in the 20-second autonomous period** — it only tells you the driving
alone takes at least N seconds.

That floor is still enough to disqualify some autos outright. Two exceed 20 s on driving alone,
before any command time is added:

| Auto | Driving time |
|---|---|
| `45 Defensive` | 21.67 s |
| `L Trench 2 Dip + Depot` | 20.74 s |

Several more sit close enough (`R Trench 2 Dips + Outpost` 18.39 s, `L R Back to Middle NC`
18.37 s, `R Trench 2 Dips` 17.25 s) that adding shoot/intake time will likely push them over.
Whether that's a real problem depends on the `driveCurrentLimit` question below — if 35 A is
wrong, these times are all pessimistic.

**Timings are unvalidated against the PathPlanner GUI.** Nobody has yet compared a generated
total against the number PathPlanner reports for the same auto. Until that golden check is done,
treat these as indicative, not authoritative.

## Looks like PathPlanner, on purpose

The field is PathPlanner's own `field26.png`, drawn with its exact calibration (3508×1814 at
200 px/m, 0.5 m margin — which works out to 16.54 × 8.07 m, matching PathPlannerLib's
`FlippingUtil.fieldSizeX/Y`). The palette, the red→orange→yellow→green **velocity ramp**, and
the green-start/red-end waypoints all follow the editor, so anyone who uses PathPlanner already
knows how to read this. PathPlanner is MIT licensed; see [THIRD-PARTY.md](THIRD-PARTY.md).

The velocity ramp is the useful part: it shows at a glance where a robot is crawling.

## Phones

Works on a phone. The auto list is behind the ☰ menu, controls are touch-sized, and the field
**rotates 90° in portrait** — a 2:1 landscape field would otherwise use about a fifth of the
screen height. Verified at a 390 px viewport with no horizontal overflow.

The robot is drawn from the real `robotFeatures` in `settings.json` — frame outline, intake,
turret — inside the bumper perimeter, so heading and intake orientation are readable directly
rather than inferred from an arrow. Features follow PathPlanner's own painters, including the
quirk that `size.length` maps to the **x** extent and `size.width` to the **y** extent.

## Known gaps (MVP)

- No CI. `regen.sh` is manual, so `autos.json` goes stale until someone runs it. The source SHA
  is stamped and shown in the UI so staleness is at least visible.
- Event labels show only within 1.2 s of the playhead; markers that fire close together can
  still overlap.

## Two things worth the team's attention

- **`driveCurrentLimit` is 35 A** in `2026-Robot`. Most swerve drives run 60–120 A, and
  `2026-Robot-Simulation` uses 120. If that's stale or a typo, PathPlanner has been generating
  over-conservative trajectories all season and the real autos may be slower than the hardware
  can achieve. This app uses the value as-is, so it reflects real current behaviour either way.
- **`main` is ~4 months stale** (2026-03-23, 29 autos) versus `dev` (2026-06-23, 41 autos).
  `main` is 0 commits ahead of `dev`. This tool tracks `dev`.
